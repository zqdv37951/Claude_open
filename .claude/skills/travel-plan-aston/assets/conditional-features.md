# 條件式功能

本檔的三項功能**不是每份行程都要做**。先判斷觸發條件，滿足才做——不滿足硬做只會讓頁面臃腫、讓讀者不知道該看哪一套。

除此之外的規則一律適用，見 `page-contract.md` 與 `engine-contract.md`。

## 用 `transit` 取代 `flights` / `hotelAreas` {#transit}


當行程不涉及搭機、不需過夜時（僅限這種情況才套用本節，其餘情況照常用 `flights`/`hotelAreas`）：

```js
trip.transit = {
  outbound: [
    { time: "09:00", leg: "東京駅 —— JR 東海道線（國府津・小田原・熱海方向）", duration: "約55分" },
    { time: "09:55", leg: "藤沢駅 轉乘 江ノ島電鉄（江ノ電，鎌倉方向）", duration: "約10分" }
  ],
  return: [ /* 同構 */ ],
  note: "單程約1小時20分，IC卡參考票價約¥990。實際票價與發車時刻請出發前以乘換案內App確認。"
};
```

- 對應區塊改標題為「交通」，去程／回程各自用時間軸清單呈現。
- `validate.js` 對缺少 `flights`/`hotelAreas` 只會給 WARNING，不是 ERROR；省略時應在頁面上加一行說明（如 `.adapt-note`），註明「本次為當日往返行程，故以交通區塊取代」，讓讀者理解這是有意的調整而非遺漏。

## 雙方案 A／B 與每日雙強度路線 {#dual-plans}


**觸發條件**（滿足任一才做，不要每份行程都膨脹成兩個版本）：

1. 行程撞上**當地連假或大型節慶**，「參加」與「錯開」會匯出兩套完全不同的排法；
2. 行程落在**季節交界**，某些設施可能已收季，需要備援排法；
3. 使用者**明確要求**比較兩種安排。

滿足時，在時間軸區塊產出兩個並列的完整方案，各自有名稱與一句話理由（如「方案 A・錯開人潮」／「方案 B・山中過節」），**兩套都要寫完整的逐日內容**，不要只寫差異——讀者是拿著其中一套走完全程的。結尾給一段「兩案並陳的結論」，明說推薦哪一套與理由，以及兩案共通的鐵則。

資料結構上用 `trip.plans` 承載，每個 plan 各有自己的 `days`；沒觸發條件時維持原本的 `trip.days` 單一方案：

```js
trip.plans = [
  { key: "a", name: "方案 A・錯開人潮", recommended: true,
    reason: "山區平日人少、住宿便宜三到四成，長週末的節慶活動本來就集中在城市",
    days: [ /* 完整逐日 */ ] },
  { key: "b", name: "方案 B・山中過節", days: [ /* 完整逐日 */ ] }
];
```

### 每日雙強度路線 + 天氣備案

同樣是條件式，觸發條件是**行程含戶外健行／登山／長時間戶外活動**。滿足時，每一天給兩條並列路線與一段備案：

- **輕鬆路線**：以觀景臺、纜車、平路、室內為主，單段步行不超過 3 km。
- **中等路線**：半天 5–10 km 等級的健行，標明距離與**累計爬升**（爬升比距離更能反映難度）。
- **天氣備案**：一段 `<div class="wx">`（class 名稱見下方「渲染 class 規格」），明說「下雨／下雪時改成什麼」，且備案必須是**低海拔、路況安全、當天可達**的實際替代點，不能只寫「改室內活動」這種空話。

這跟 `page-contract.md` 既有的 `day.alternatives`（二選一卡片）不同：`alternatives` 是同一強度下的兩個選擇，這裡是**同一天的兩種體力強度**，兩者可以並存。

### 欄位定義

`trip.plans` 與每日 `routes` 的完整欄位（`page-contract.md#trip-data` 有放在整體結構裡對照）：

```js
trip.plans = [
  { key: "a",                 // 短代號，用來組 DOM id（面板 id、錨點）
    name: "方案 A・錯開人潮",   // 顯示名稱
    recommended: true,        // 只有一個為 true；用來決定地圖顯示哪一套站點
    reason: "…",              // 一句話理由，渲染在方案標頭下
    days: [ /* 與 trip.days 同結構，完整逐日 */ ] }
];

// 每日雙強度路線（掛在 day 上，不在 slot 上）
day.routes = [
  { kind: "easy",             // "easy" | "mid"，決定標頭的修飾 class
    label: "輕鬆路線",         // 顯示文字
    stops: [ { time, name, url, note } ] }   // url 可省略；省略時標題維持純文字
];
day.planB = "下雪時改走…";     // 雨雪備案，一段完整可執行的替代方案
```

**`recommended` 必須有且只有一個為 `true`** ——`validate.js` 會檢查。它決定地圖用哪一套站點（兩套疊在一起看不懂），也決定哪個方案標頭加「推薦」標記。

### 渲染 class 規格

跟引擎輸出的 class 一樣，**這幾個 class 由頁面自己產生、也由頁面自己上樣式**；定死名稱是為了各頁面視覺一致、也方便機械抽查：

| class | 用在哪 | 結構性要求 |
|---|---|---|
| `.plan-head` | 方案標頭卡片 | 每個 plan 一個，含名稱、`reason`，推薦方案要有可辨識的標記 |
| `.route` | 單一強度路線的容器 | 桌機並排兩欄（`grid-template-columns:1fr 1fr`），手機單欄堆疊 |
| `.route-h` + `.easy` / `.mid` | 路線標頭 | 修飾 class 對應 `kind` 欄位的兩個值 |
| `.wx` | 雨雪備案區塊 | 每天最多一個，對應 `day.planB` |
| `.daytip` | 當日貼士 | 對應 `day.tips`，可多個 |

**這幾個 class 長什麼樣由 `references/design-guidelines.md#dual-plan-visuals` 決定**——本檔只管「有哪些 class、對應哪個欄位、版面結構怎麼排」，配色與視覺權重不在這裡重複規定。

並排兩欄時**務必給 `.route` 的父容器 `min-width: 0`**，理由同 `engine-contract.md#poi-wall`——否則長站名會把欄位撐開。

## 季節狀態標籤 {#season-status}


**觸發條件**：目的地有明確的季節性營運（山區、國家公園、滑雪場、海濱、賞櫻賞楓等），且行程日期靠近季節交界。

滿足時，`highlights` 項目與時間軸站點都可帶 `status` 欄位，渲染成卡片上的小標籤：

```js
{ name: "夢蓮湖", lat: 51.3217, lng: -116.1860,
  status: { label: "10/12 封路", kind: "season" } }
```

`kind` 三種：`season`（季末／封路，用警示色）、`booking`（須提前訂）、`free`（免費／不需票）。

### 分類依「語意」，不依來源的樣式

從既有頁面或舊資料搬 `status` 過來時，**絕對不要拿原本的顏色 class 當 kind 用**。踩過一次：舊卡片的標籤是用顏色分組的，`c-gold` 那一組同時混了「10/12 季末」、「$$$」、「中等偏難」三種完全不同維度的東西。照顏色映射的結果是 **6 個價位標籤變成了季末警示** ——「$$$」跟「10/12 封路」用同一個警示色，警示效果整個消失。

依文字判斷：

| kind | 判斷關鍵字 |
|---|---|
| `season` | 季末 · 收季 · 季節限定 · 已停 · 封路 |
| `booking` | 必須提前訂 · 須訂位 · 須先確認營運 |
| `free` | 免費 |

**其餘一律不是 status**：價位（`$`／`$$$`）、難度（輕鬆／中等／零體力）、攜帶限制（不可帶回日本）、飲食（純素）、備案標記（壞天備案）——這些是別的維度，應該放進 `category`。`poi.js` 的 `category` **接受字串或字串陣列**，一張卡片可以同時掛英文名 + 價位 + 難度：

```js
{ name: "Post Hotel 餐廳", category: ["Post Hotel Dining Room", "$$$$"],
  status: { label: "必須提前訂", kind: "booking" } }
```

判斷原則：**這個標籤講的是「這個地方現在還開不開」嗎？** 是就是 status，不是就是 category。

**這個標籤只能由查證過的事實填充。** 查不到確切日期就不要放標籤，改在 `note` 裡寫「營運日期請出發前確認」並附官方連結。標籤的價值來自它是真的——一旦出現猜測的日期，整頁的可信度都會被拖累。

搭配 `references/research-guide.md` 的查證紀律使用：季節性目的地的調研，**收季日期跟營業時間同等重要**，不是可選的加分項。

## 常見誤區

**不要因為行程是多日／跨國／有航班，就跳過 `page-contract.md` 與 `engine-contract.md` 的規則。** 那兩份是無條件的；本檔這三項才是條件式。判斷順序：先無條件套用那兩份，再逐一判斷本檔三項要不要觸發。

**反方向的誤區同樣要避免：不要把本檔三項當成一律要做的。** 短程、平地、非季節性的行程做雙方案只會讓頁面臃腫。條件不滿足就維持單一方案的 `trip.days`。
