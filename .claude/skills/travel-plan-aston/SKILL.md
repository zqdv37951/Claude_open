# 旅行计划可视化

把一趟旅行变成单文件 HTML 页面：交互地图、每日时间轴、出发前订票提醒。机械逻辑用自带引擎（`assets/map.js`、`assets/reminders.js`、`assets/poi.js`），美学交给设计步骤（`frontend-design` / `huashu-design`，或内置准则兜底）。

## 第一步：判断模式

- 用户**只给了目的地+天数**（如"香港 4 天 3 晚"）→ 模式 A（从零规划）。
- 用户**已提供行程**（文字或旧 HTML 文件）→ 模式 B（解析已有计划）。

## 模式 A：从零规划

1. **先把 brief 问清楚，再开始调研。** 行程页面是大产出，误解会被放大——做到第 300 项才发现颗粒度错了，代价是全部重来。把未知分三类，区别对待：

   | 类别 | 处理 |
   |---|---|
   | 改变**有哪些工作** | 必须问，问完才动 |
   | 改变**已知工作里的细节** | 便宜就问，否则明说假设 |
   | 自己能决定的 | 直接定，讲一句，往下走 |

   用 `AskUserQuestion`（或等价的选项式提问）**每轮最多 4 题**——两轮短的胜过一轮十题。轮与轮之间，把你**现在打算做的骨架**摊出来让对方确认形状，而不是只确认参数。旅行行程真正会改变工作量的通常只有这四项：**交通方式**（自驾/包车/大众运输，决定行程能排什么）、**清单颗粒度**（每天各十项 vs 每区各十项，篇幅差三倍）、**住宿状态**（已订/未订，决定要不要给选项）、**输出格式**。其余可以先假设。

   问完之后，**把剩下的假设列成一张表**写在对话里再动手——对方没反对的就算达成共识。

2. 读 `references/research-guide.md`，联网调研目的地。
3. 在对话里用 markdown 提出详实逐日计划（早/中/晚、景点、交通、住宿）。
4. 与用户来回迭代，直到用户明确确认。
5. 进入"调研补全 + 生成"。

## 模式 B：已有计划

1. 解析用户给的行程。**若是本 skill 生成的旧 HTML**：直接解析其中 `<script id="trip-data" type="application/json">` 的完整 `trip` JSON（数据与呈现分离，别去反解析渲染后的 DOM——必丢字段）；旧版页面没有这块时才从 DOM/文本提取——**从 DOM/文本提取时，除 `url` 外的所有字符串都要先 `html.unescape()` 一次再存进 `trip`**，否则引擎的 `escapeHTML` 会再转义一遍，页面上出现 `Chinatown &amp; Cultural Centre` 这种双重转义（见 `trip-extras.md` 第 12 节）。
2. **顺手提建议（Agent 增值，但别硬来）**：把用户的计划对照"完善行程"的维度（行前须知/天气应对、提前订票项、点到点交通、节奏与缓冲、当地必吃、片区住宿是否合理等）快速体检，在**对话里**给**最多 3–4 条**具体、可选的优化建议。原则：
   - 只挑**真实存在的缺口**；计划本就完整就直说"挺完整"，**不要硬凑、不要说教、不要替用户重排行程**。
   - 一句点出问题 + 一句给方向即可，简洁；建议默认口头给，保持 HTML 成品干净（用户想把建议也放进页面再加）。
   - 这是我们区别于"纯提示词转 HTML"的地方——发挥 Agent 的判断力，但点到为止。
3. 进入"调研补全 + 生成"（生成不被建议阻塞；采纳哪些由用户定）。

## 调研补全 + 生成

1. **先判断第三方 skill 适配**（详见 `references/research-guide.md`「第三方 skill 适配」节）：若当前 Agent 可调用用户**已装**的官方旅行 skill / MCP（飞猪、高德、腾讯地图、滴滴等），**优先用它们拿对应数据**——高德地理编码拿精确坐标（**注意：高德/腾讯返回 GCJ-02 坐标，写入 `trip` 前必须用 `map.js` 的 `gcj02ToWgs84` 转成 WGS-84**，否则在 OSM 地图上偏移几百米）、路线规划增强点到点交通、天气查询、生成专属地图/导航/叫车的行动链接；飞猪拿实时航班/酒店/门票及预订链接。把用到的来源登记进 `trip.dataSources`，行动链接写入对应节点的 `actionLink`（**链接只用官方返回的，绝不手拼**）。**没有这些 skill 就全部走下面的静态调研**，成品不缺区块。数据实时性/真实性由对方官方 skill 负责，本 skill 不背书、措辞中性。
2. 按 `references/research-guide.md` 联网补全（官方 skill 未覆盖的部分）：坐标、真实图片 URL、评分、点评、营业时间/休息日、门票参考价、需提前订项及 `leadDays`；**行前须知**（天气/台风/穿搭/支付/App/购票时机）、**点到点交通**（方式/票价/耗时）、**时令限定活动**、每餐**必点菜+参考价**；航班给 3-5 个**待选班次**、酒店按**片区+价位**推荐、并准备**免责声明**与全程**贴士**。排程体现**天气/季节逻辑**（户外排凉爽时段）。**本 skill 自身不查实时票价**（实时数据只来自上面用户已装的官方 skill）。
2.5. **查证纪律：看事实之间的「模式」，不只看单条事实。** 营业时间、季节收季日、票价、封路——每一条都要搜过再写，绝不凭记忆。更重要的是**把查到的结果横向摆在一起看**：曾经有一趟落基山行程，五个独立查询（缆车、冰川行程、湖区道路、接驳订位、历史村）全部回传同一个日期——那天正好是旅客的回程日，整个行程的排法因此完全改写。**那个模式才是这趟调研最有价值的产出，而任何单一查询都揭露不了它。** 季节性目的地尤其要把「收季日」当成跟营业时间同等的必查项（对应 `trip-extras.md` 第 10 节的 `status` 标签）。查不到就如实标「请出发前确认」并附官方连结，含糊而诚实胜过肯定而错误。

3. 组织成 `assets/page-contract.md` 里定义的 `trip` 数据结构（含可选的 `dataSources` 与节点 `actionLink`）。**同时无条件读 `references/trip-extras.md`**（不限行程类型、不限单日或多日、国内或跨国）：加入 `trip.highlights`（特色景点/美食/店家总览，各至少10项）、每站「附近推荐」toggle 面板、时间轴站点标题连结、页面区块顺序规范、`trip.glossary`（外文名词注解，视语言环境触发）、预设配色。**只有「不涉及航班/住宿的单日往返或国内短程行程」这个子情况**才额外改用 `trip.transit` 取代 `flights`/`hotelAreas`（trip-extras.md 第1节）。
4. 用**设计步骤**生成风格化 HTML：**优先**调用专业设计 skill——`frontend-design` 或 `huashu-design`（花叔Design），任一已安装即用；**两者都没有**时，按 `references/design-guidelines.md` 的内置美学准则自己出。无论哪种方式都要严格遵守 `assets/page-contract.md` 的区块与约束：
   - 内联 `assets/map.js`、`assets/reminders.js`、`assets/poi.js` 内容到 HTML（保证单文件）。**内联完立刻照 `trip-extras.md` 第 11 节那张表核对 CSS**——三个引擎只输出语义 class，样式全由页面负责；漏了 `map.js` 的 `.route-pin` 会让地图上 N 个标记**全部隐形**（元素数量还是对的，纯读代码与元素计数都抓不到），漏了 `reminders.js` 的 `.todo-*` 会让页顶待办清单退化成裸列表。
   - 完整 `trip` 对象以 `<script id="trip-data" type="application/json">` 内嵌进页面（后续迭代修改的数据源）。
   - 页顶清单用 `computeReminders` + `renderChecklistHTML`。
   - 展示行前须知区块；航班区展示待选班次（已预订的高亮），酒店区按片区+价位展示，附近显著展示免责声明。
   - 时间轴卡片展示营业时间/门票参考价/交通/时令活动等可选字段；展示每日餐饮（必点菜+价）、当日与全程贴士、单日二选一方案（若有）。
   - 地图用 `initTravelMap`，引入 Leaflet CDN 的 CSS/JS。
   - 时间轴上 `needsBooking` 项插入 `reminderBadgeHTML(leadDays)`。
   - **延伸推荐区块**（详见 `trip-extras.md` 第 2、3 节）：调用 `poi.js` 的 `poiWallHTML`/`nearbyGridHTML`，不要重新手刻——分「精选 highlights」与「行程途经」（附近面板算出来、命中 `day.slots` 但不在 highlights 里的项目）两组标记显示，去重；三个分类都用「2 列 × 横向卷动」版面（超过 2 项自动带滚动提示）；每张卡片有坐标就额外加一行调用 `buildMapAppLinks` 生成的地图连结；每站附近推荐面板也用同一套卡片与标签。
   - **可选适配元素**：节点带 `actionLink` 时渲染「去预订/导航/叫车」按钮（缺则不渲染、不手拼）；`dataSources` 非空时中性注明数据来源。
   - 每趟行程用不同配色。
4.5. **分块写文件，不要一次吐完整页。** 多日行程页动辄数千行，一次生成很容易在中段出错且难以定位。用追加的方式分段写（每段约 200–400 行：`<title>`+CSS → tab 导览+页顶清单 → 行前须知/交通 → 逐日时间轴 → 地图 → highlights → 贴士/注解），**每段写完立刻回报行数**。CSS 那段写完马上 grep 一次有没有混进异常字符——一个错字塞在 CSS 值里会静默废掉整条声明，肉眼看不出来。

5. 保存为 `<行程名>-旅行计划.html` 到工作目录。
6. **机械校验（必做）**：跑 `node <skill目录>/assets/validate.js <生成的.html>`——校验 trip 必填字段、坐标越界/离群、必需区块标记、trip-data 内嵌。有 ERROR 必须修复后重跑至通过；WARNING 逐条人工判断。**另外自己断言两件事**：①**数量**——brief 里说「每区十项」就写一行脚本数出来确认是十项，不要靠肉眼扫；②**引擎 class 样式齐全**——把三个引擎的 class 抽出来逐一比对页面 `<style>`（脚本见 `trip-extras.md` 第 11 节）。这两类错误在几千行的页面里用看的永远看不出来。
7. **浏览器实测（必做，不能只靠上一步或读代码）**：用 Playwright（当前环境已预装 Chromium，见环境说明；没有时至少提醒用户自行打开确认）实际打开生成的 HTML，检查：① 附近推荐面板默认是**收合**的（`hidden` 真的生效——曾经出现过 CSS 另外写了 `.nearby-panel{display:flex}` 盖掉浏览器对 `[hidden]` 的默认样式，面板一开始就是展开的，但按钮文字还写着「显示」，纯读代码看不出来）；② 点开面板后卡片牆是「横向卷动」而不是纯直向堆叠（曾经出现过 CSS 版面行数没套用、退化成普通网格）；③ 地图连结、来源标签（精选/行程途经）确实渲染出来，不是空字串；③b **地图上的编号标记真的看得见**（不是只有虚线路线）——`.route-pin` 没样式时标记是透明的，`.leaflet-marker-icon` 数量却完全正常，只有真的看画面才抓得到；④ 手机宽度（如 390px）下没有破版；⑤ 顶部 tab 导览在手机上是**横向卷动**而不是换行挤成两三列，且点击锚点跳转后标题没有被 sticky 条盖住（`scroll-margin-top` 有生效）。这一步不能省略——上面两个真 bug 都是纯读代码判断不出来、只有实际打开页面才抓到的。
8. **回报时先讲「调研改变了什么」，不是先讲做了哪些区块。** 用户要的是判断依据：哪一条查证结果推翻了原本的排法、哪些事实查不到需要他出发前自己确认、你替他做了哪个他没要求的取舍。功能清单排在这些后面。**查不到的就明说查不到**，不要用模糊措辞盖过去。

9. 告诉用户：之后可把该 HTML 文件丢回来，说"把第三天的 X 挪到第四天"，会在原结构上修改（直接改内嵌的 trip-data JSON 再重渲染）。

## 不做

本 skill **自身**不做：实时票价/机票价格查询、代订票、多语言 UI、后端。全程静态单文件。

> 注意边界：用户若另装了官方旅行 skill（飞猪/高德/腾讯地图/滴滴等），实时数据与「预订/导航/叫车」链接**由其提供、责任在其**——本 skill 只适配呈现，并不改变上面「自身不做」的范围（仍不自查实时价、不代订）。
